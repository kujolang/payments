# Link payment journal admission

The Link adapter stores SpendRequest issuance references, MPP preparation/dispatch tombstones and immutable provider preparation bindings in one private database. These references are needed to observe an uncertain payment without recreating its native operation. Startup now validates their frozen SQL profile before creating an absent supported group; it does not silently recreate a missing trigger/index or accept a different table definition.

`open_link_authorizations` admits an empty database, a complete authorization group, the combined authorization/submission profile, or the full provider profile. `open_link_submissions` requires the authorization group first, for standalone component use. The provider factory instead creates all thirteen objects atomically in a new empty database and requires the complete thirteen-object profile when reopening. It refuses an existing authorization-only or authorization/submission-only journal rather than guessing whether provider preparation history was lost. Submission-only or fragmented legacy databases fail closed and need private operator review; the adapter does not infer that their missing authorization history is empty. Unrelated tables and SQLite user versions other than the existing legacy value zero are rejected. Credential, enrollment and approval-outbox journals stay separate.

The frozen profile retains the exact existing SQL, identifiers, rows, native references and claims from source `3650888661ab219b74421730d03eff2205b8a3d2`. The fixture `tests/fixtures/link-payment-journal-v0.json` records that profile. This is explicit recognition of an existing legacy layout, not a new v1 migration or a change to payment/Ability identity. A future layout must introduce a separately reviewed migration. SQLite's internal objects are excluded from profile comparison.

Validation and any group creation share a bounded `BEGIN IMMEDIATE` transaction. A validation or DDL error rolls back creation. If enabling WAL fails after commit, startup fails but the validated initialized database may remain; that is not permission to execute a payment. Existing busy-timeout, FULL synchronization, foreign-key and authorization WAL behavior are retained. Openers own their transaction and should be called outside an application transaction. They do not call Link, authorize spending or repair a partial financial history.

## Evidence and limits

The conformance fixture opens a populated database created from the frozen legacy SQL and checks retained issuance/native/dispatch identities. It tests every missing/changed object, foreign/future profiles, submission-first refusal and four-process initialization. Normal payment, issuance-race, approval, submission and provider tests exercise the supported factory path. Source-scoped verification status is recorded in implementation-status.md.

This check detects structural drift; it cannot prove completeness of historical rows. An entirely lost database or removed complete optional group can resemble a new or smaller valid database. The core's permanent claims and native-authorization reservations remain essential independent controls. Never treat an empty journal, a validated schema or a backup hash as evidence that money did not move. Do not drop constraints, delete tombstones or retry uncertain issuance to make a damaged journal open.

Coordinated private-journal backup, authenticated provider observation, missing-history reconciliation and supported disaster recovery remain release requirements. This admission check is a prerequisite, not a replacement for them.
